# 내가 공부한 웹소켓 정리

## 웹소켓(WebSocket)?
- 클라이언트가 요청을 보내야만 서버가 응답하는 기존 HTTP 통신(단방향/무상태)과 달리, 한 번 연결되면 서버와 클라이언트 양쪽에서 언제든 실시간으로 데이터를 주고받을 수 있는 통신 프로토콜.
- 최초 접속 시 HTTP 통신을 통해 연결(Handshake)을 맺은 후, 프로토콜을 웹소켓(ws:// or wss://)으로 업그레이드하여 연결을 계속 열어 둠.
- HTTP 통신 시 매번 포함되는 무거운 헤더 정보가 초기 연결에만 사용되고, 이후 통신에서는 웹소켓 전용 프레임만 사용하므로 데이터 통신량이 적고 속도가 매우 빠름.


## 웹소켓과 RESTful은 어울리지 않음
- RESTful: 클라이언트가 서버의 특정 자원(URI)에 요청을 보내면 서버가 응답을 반환하고 즉시 연결을 끊는 단방향/무상태(Stateless) 통신 철학을 기반으로 함.
- 웹소켓: 한 번 맺은 연결을 끊지 않고 계속 상태를 유지(Stateful)하며, 서버와 클라이언트가 서로 원할 때 언제든 실시간으로 데이터를 밀어넣는(Push) 양방향 통신.
- REST는 '요청-응답' 기반이고 웹소켓은 '이벤트 기반의 실시간 스트리밍'이므로 아키텍처의 목적과 생명 주기 자체가 완전히 다름.


## 그렇다면 프론트(React)는 어떻게 요청을 보내야하나?
- REST API처럼 axios나 fetch를 사용하여 특정 기능마다 각각 다른 URL 경로로 HTTP 요청을 보내는 방식이 아님.
- 최초에 서버의 웹소켓 엔드포인트(예: /ws/raw 또는 /ws-stomp)로 연결을 한 번 맺은 후, 열려있는 웹소켓 통로를 통해서만 통신해야 함.
- 정통 웹소켓 (페이로드 내부 필드 기반)
  - 프론트엔드와 서버를 잇는 통로가 단 하나뿐임.
  - 보낼 때: 사전에 약속한 JSON 규격에 맞춰 메시지 타입(type: "TALK")을 데이터 내부에 명시하여 전송해야 서버의 Handler가 로직을 분기할 수 있음.
  - 받을 때: onmessage 이벤트 하나로 모든 메시지를 다 받아서 프론트엔드가 if/switch 문으로 직접 걸러내야 함.
- STOMP (목적지 주소 기반)
  - STOMP 프로토콜 자체가 경로 개념을 지원함. 목적에 맞는 가상의 목적지 주소(Destination)를 나누어 통신함.
  - 보낼 때: 내용물에 type을 억지로 넣을 필요 없이, 목적에 맞는 엔드포인트로 메시지를 publish(발행) 함 (예: /app/chat.room.123.talk).
  - 받을 때: 특정 방이나 알림 채널을 구독 함. 콜백 함수를 지정하면 해당 경로로 오는 메시지만 깔끔하게 분리되어 들어옴.


## 정통 WebSocket vs WebSocket Broker(STOMP)

### 정통 WebSocket
- 별도의 규격화된 포맷이나 무거운 프로토콜이 없기 때문에 데이터 크기가 작아 극도의 실시간성과 빠른 처리 속도가 필요한 환경에 유리함.
- Controller 개념이 없음. WebSocketHandler라는 하나의 클래스가 서버의 중심점 역할을 하며 모든 비즈니스 로직과 라우팅을 담당함.
- 접속한 사용자의 WebSocketSession을 서버 메모리의 List나 Map에 직접 저장하고, 메시지를 보낼 때마다 반복문을 돌며 발송해야 함.
- 서버가 2대 이상으로 늘어나면 메모리가 공유되지 않아 유저 간 통신이 단절됨. 이를 해결하려면 Redis Pub/Sub 등을 핸들러에 직접 코딩하여 연동해야 함.
- ex. 실시간성이 아주 중요할 때 (게임, 주식 코인 시세, FPS 위치 동기화, 실시간 드로잉 등)

### WebSocket Broker (STOMP)
- HTTP의 URL처럼 동작하는 주소(Destination) 기반 라우팅을 지원함. 프론트엔드는 주소로 Publish/Subscribe만 하면 됨.
- Spring MVC처럼 @Controller와 @MessageMapping을 사용하여 요청 주소별로 비즈니스 로직을 깔끔하게 분리할 수 있음.
- 경로로 목적을 구분하므로 DTO 내부에 type 필드가 필요 없음.
- 세션(Map)을 개발자가 직접 관리할 필요가 없음. 스프링 내장 브로커가 구독자 목록을 알아서 관리하고 메시지를 뿌려줌.
- 서버가 여러 대가 되어도 비즈니스 로직(Controller)은 단 한 줄도 수정할 필요가 없음. 설정 파일(Config)에서 내장 브로커를 끄고 외부 브로커(RabbitMQ, Redis 등)로 연결 포트만 열어주면 확장이 끝남.
- ex. 채팅, 실시간 알림, 다대다 통신이 중심이 되는 대부분의 일반적인 웹/앱 서비스.
