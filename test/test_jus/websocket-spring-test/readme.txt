# 내가 공부한 웹소켓 정리

## 웹소켓(WebSocket)?
- 클라이언트가 요청을 보내야만 서버가 응답하는 기존 HTTP 통신(단방향/무상태)과 달리, 한 번 연결되면 서버와 클라이언트 양쪽에서 언제든 실시간으로 데이터를 주고받을 수 있는 통신 프로토콜
- 최초 접속 시 HTTP 통신을 통해 연결(Handshake)을 맺은 후, 프로토콜을 웹소켓(ws:// or wss://)으로 업그레이드하여 연결을 계속 열어 둠
- HTTP 통신 시 매번 포함되는 무거운 헤더 정보가 초기 연결에만 사용되고, 이후 통신에서는 웹소켓 전용 프레임만 사용하므로 데이터 통신량이 적고 속도가 매우 빠름

## 웹소켓과 RESTful은 어울리지 않음
- RESTful은 클라이언트가 서버의 특정 자원(URI)에 요청을 보내면 서버가 응답을 반환하고 즉시 연결을 끊는 단방향/무상태(Stateless) 통신 철학을 기반으로 함
- 반면 웹소켓은 한 번 맺은 연결을 끊지 않고 계속 상태를 유지(Stateful)하며, 서버와 클라이언트가 서로 원할 때 언제든 실시간으로 데이터를 밀어넣는(Push) 양방향 통신
- REST는 '요청-응답' 기반이고 웹소켓은 '이벤트 기반의 실시간 스트리밍'이므로 아키텍처의 목적과 생명 주기 자체가 완전히 다름

## 그렇다면 프론트(React)는 어떻게 요청을 보내야하나?
- REST API처럼 axios나 fetch를 사용하여 특정 기능마다 각각 다른 URL 경로(/api/chat, /api/room 등)로 HTTP 요청을 보내는 방식이 아님.
- 최초에 서버의 웹소켓 엔드포인트(예: ws://서버주소/ws/raw 또는 ws://서버주소/ws-stomp)로 연결을 한 번 맺은 후, 열려있는 웹소켓 연결을 통해서만 데이터를 서버로 밀어넣어야 함.
- 정통 웹소켓 방식 (페이로드 내부 필드 기반 라우팅)
  - 프론트엔드와 서버를 잇는 통로가 단 하나뿐임. 서버는 수신한 순수 문자열만 보고는 데이터의 목적을 알 수 없음
  - 사전에 서버와 약속한 JSON 규격에 맞춰 메시지 타입(type)을 데이터 내부에 명시하여 전송해야 서버의 Handler가 로직을 분기할 수 있음
  - 브라우저 내장 WebSocket 객체의 send() 메서드를 사용
- STOMP 방식 (목적지 주소 기반 라우팅)
  - STOMP 프로토콜 자체가 '경로' 개념을 지원함. HTTP 통신에서 URL을 나누듯, 웹소켓 위에서도 가상의 목적지 주소를 나누어 통신할 수 있음
  - 페이로드(내용물)에 type을 억지로 넣을 필요 없이, 목적에 맞는 엔드포인트 주소(Destination)로 메시지를 publish(발행) 함. 서버는 컨트롤러의 @MessageMapping을 통해 주소별로 요청을 가로챔
  - @stomp/stompjs 등 전용 라이브러리의 publish() 메서드를 사용


## 정통 WebSocket vs WebSocket Broker(STOMP)

### 정통 WebSocket
- 별도의 프로토콜(규격화된 포맷)이 없기 때문에 데이터 크기가 작아 극도의 실시간성과 빠른 처리 속도가 필요한 환경에 유리
- controller 개념이 없음. WebSocketHandler가 서버의 중심점 역할을 함 (WebSocketHandler에 비지니스 로직)
- 메시지의 규격이 없어서 순수한 텍스트(String)나 바이너리(Byte) 데이터만 주고받음. 따라서 메시지의 목적(입장, 대화 등)을 구분하려면 개발자가 직접 JSON 형태의 DTO를 설계하고 파싱하는 로직을 만들어야 됨
- 직접 세션을 분류하고 추적하는 로직을 구현해야 함. (접속한 사용자의 WebSocketSession을 서버 메모리의 List나 Map에 직접 저장하고, 메시지를 보낼 때마다 반복문을 돌며 발송)
- ex) 실시간성이 아주 중요할 때, 성능이 중요할 때 (게임, 주식 시세, FPS 위치 동기화, 실시간 드로잉 등...)
